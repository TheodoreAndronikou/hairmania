# Έγγραφο παράδοσης — HAIR MANIA VALKANIS

Για προγραμματιστή που παραλαμβάνει το έργο, ή για μένα τον ίδιο σε έξι
μήνες. Γράφτηκε ώστε να μπορεί κάποιος να συνεχίσει **χωρίς εμένα**.

Τελευταία ενημέρωση: 22 Οκτωβρίου 2026

---

## 1. Τι είναι

Στατικό site με online κρατήσεις για κουρείο ενός ατόμου. Χτίστηκε για το
HAIR MANIA VALKANIS στα Γιαννιτσά και είναι πλέον πρότυπο: ένα νέο
κατάστημα στήνεται από το ίδιο project. Δύο κοινά: οι πελάτες κλείνουν
ραντεβού, ο ιδιοκτήτης διαχειρίζεται τη μέρα του από κινητό.

**Χωρίς build.** Σκέτα HTML/CSS/JS, κανένα npm, κανένα framework. Ανοίγεις
αρχείο, το αλλάζεις, το ανεβάζεις.

Μέγεθος: ~4.200 γραμμές στο site, από τις οποίες ~800 CSS και ~340
μεταφράσεις· η λογική είναι ~2.300 γραμμές JavaScript. Η βάση είναι
~780 γραμμές SQL.

## 4. Πώς ανεβάζω αλλαγές

**Δύο ξεχωριστές κινήσεις, και χρειάζονται και οι δύο:**

```bash
git add -A
git commit -m "τι άλλαξα"
git push
```

Αυτό **σώζει τον κώδικα** στο `hairmania-source`. Χωρίς αυτό, η αλλαγή
υπάρχει μόνο στον υπολογιστή σου.

```bash
node publish.mjs "τι άλλαξα"
```

Αυτό **ανεβάζει το site**: τρέχει το `rebrand.mjs`, αντιγράφει το
`site/` και τα `docs/` στο `_publish/`, και τα στέλνει στο δημόσιο
`hairmania`. Ζωντανό σε 1-3 λεπτά. Διατηρεί αυτόματα το αρχείο `CNAME`,
ώστε το custom domain να μη ξεκολλάει.

Το ένα **δεν** κάνει το άλλο. Αν τρέξεις μόνο το `publish.mjs`, το site
ενημερώνεται αλλά ο κώδικας δεν σώζεται πουθενά.

## 5. Οι συνηθισμένες αλλαγές

### Τιμές, υπηρεσίες, ωράριο

**Ζουν σε ΔΥΟ μέρη, και πρέπει να συμφωνούν:**

| Πού | Ποιος τα διαβάζει |
|---|---|
| βάση — πίνακες `services`, `hours` | η σελίδα κράτησης: ελεύθερες ώρες, επιλογές, τιμή που γράφεται στο ραντεβού |
| `config.js` — ενότητες `hours`, `services` | η αρχική, η επικοινωνία, η ένδειξη «Ανοιχτά τώρα», ο τιμοκατάλογος, τα δεδομένα Google |

Το `config.js` **δεν** είναι εφεδρικό. Αν αλλάξεις μόνο τη βάση, η αρχική
θα συνεχίσει να δείχνει το παλιό ωράριο ενώ οι κρατήσεις ακολουθούν το
νέο. Άλλαξε και τα δύο, και κράτα ίδια τα `id` των υπηρεσιών.

Στη βάση:

```sql
-- τιμή
update services set price = 14 where id = 'kourema';

-- προσωρινή απόκρυψη υπηρεσίας
update services set active = false where id = 'styling';

-- ωράριο· dow: 0 = Κυριακή ... 6 = Σάββατο, κενός πίνακας = κλειστά
update hours set ranges = '[["09:00","15:00"],["17:00","21:00"]]'
  where dow = 2;
```

Και μετά τις ίδιες τιμές στο `config.js`, ενότητες `hours` και
`services`, και `node publish.mjs`.

### Τηλέφωνα, διεύθυνση, social, όνομα καταστήματος

`site/assets/js/config.js`, ενότητα `business`. Τίποτα από αυτά δεν
γράφεται δεύτερη φορά αλλού — τα κείμενα των σελίδων χρησιμοποιούν
`{NAME}`, `{CITY}`, `{CITY_IN}` και συμπληρώνονται την ώρα που φορτώνει
η σελίδα.

Εξαίρεση: οι ετικέτες μέσα στο `<head>` (τίτλος, description, `og:`,
δομημένα δεδομένα Google) **πρέπει** να είναι κανονικό κείμενο, γιατί
οι crawlers του Facebook/WhatsApp δεν τρέχουν JavaScript. Αυτές τις
παράγει το `rebrand.mjs` από το ίδιο config — και το `publish.mjs` το
τρέχει μόνο του σε κάθε ανέβασμα, οπότε δεν χρειάζεται να το θυμάσαι.

### Νέο κατάστημα από το ίδιο πρότυπο

1. Αντίγραφο του `hairmania-source` σε νέο ιδιωτικό repo για το κατάστημα.
2. Στο `config.js`: `business` (όνομα, `brandTop`/`brandSub` για το
   λογότυπο δύο γραμμών, τηλέφωνα, email, διεύθυνση, `cityEn`,
   `cityIn`), `hours`, `services`, `theme`, και τα στοιχεία `SUPABASE`
   του νέου project.
3. Αντικατάστησε τις εικόνες στο `site/assets/img/`.
4. Νέο project στο Supabase και τα τέσσερα αρχεία SQL με τη σειρά —
   βήματα στο `ΟΔΗΓΙΕΣ-ΕΓΚΑΤΑΣΤΑΣΗΣ.md`, ενότητα Α. Το `schema.sql`
   βάζει υπηρεσίες και ωράριο του Βαλκάνη· **ενημέρωσέ τα** με τα
   `update` της προηγούμενης ενότητας ώστε να ταιριάζουν με το config.
5. Φιλοξενία: νέο repo για το site και αλλαγή του `REMOTE` στο
   `publish.mjs` — ή, καλύτερα, πάροχος που επιτρέπει εμπορική χρήση
   (βλ. §2).

Το `cityIn` είναι η πόλη **με το άρθρο** (`στα Γιαννιτσά`, `στη
Θεσσαλονίκη`): τα ελληνικά δεν κλίνονται αυτόματα.

**Δεν μοιράζονται βάση.** Ο κώδικας είναι για ένα κατάστημα — κανένας
πίνακας δεν έχει στήλη «ποιο μαγαζί». Κάθε κατάστημα θέλει δικό του
project στο Supabase (και παίρνει έτσι ολόκληρο το δωρεάν όριό του).

### Θέμα εμφάνισης

`config.js` → `theme: 'c'`. Υπάρχουν τρία (`a`, `b`, `c`) και αλλάζουν
γραμματοσειρές και χρώματα. Το `c` είναι το εγκεκριμένο.

### Κωδικός διαχειριστικού

Από το ίδιο το διαχειριστικό, κουμπί **ΑΛΛΑΞΕ ΚΩΔΙΚΟ**. Ή:

```sql
update settings set value = 'νεος_κωδικος' where key = 'admin_pin';
```

## 6. Η βάση

### Πίνακες

| Πίνακας | Τι κρατάει |
|---|---|
| `appointments` | ραντεβού και μπλοκαρίσματα (`kind`) |
| `services` | υπηρεσίες, τιμές, διάρκειες |
| `hours` | ωράριο ανά ημέρα εβδομάδας |
| `closures` | διαστήματα κλεισίματος (διακοπές) |
| `settings` | κωδικός, κλειδιά email, διεύθυνση site |

### Το μοντέλο ασφαλείας — διάβασέ το πριν αλλάξεις κάτι

Το δημόσιο κλειδί (anon key) βρίσκεται **μέσα στη σελίδα**, ορατό σε
όλους. Άρα:

1. **Όλοι οι πίνακες έχουν RLS ενεργό και ΚΑΜΙΑ πολιτική.** Δηλαδή
   κλειδωμένοι. Το `GET /rest/v1/appointments` με το δημόσιο κλειδί
   επιστρέφει `permission denied` — επαληθευμένο.
2. **Η πρόσβαση γίνεται μόνο μέσω συναρτήσεων** `security definer`, που
   ελέγχουν τι επιτρέπεται και επιστρέφουν μόνο όσα χρειάζονται.
3. Ο ρόλος `anon` έχει `execute` **μόνο** στις συναρτήσεις που πρέπει.

> Αν κάποια στιγμή προσθέσεις πολιτική RLS ή δώσεις δικαιώματα σε πίνακα,
> **εκθέτεις ονόματα και τηλέφωνα πελατών στο διαδίκτυο.** Μη το κάνεις.
> Πρόσθεσε συνάρτηση.

### Διπλοκρατήσεις

Αυτό είναι το κρισιμότερο κομμάτι όλου του συστήματος:

```sql
exclude using gist (tstzrange(starts_at, ends_at) with &&)
  where (status = 'active')
```

Η ίδια η βάση **αδυνατεί φυσικά** να δεχτεί δύο ενεργά ραντεβού που
επικαλύπτονται. Όχι έλεγχος στον κώδικα, όχι κλείδωμα — περιορισμός
ακεραιότητας. Δύο ταυτόχρονες κρατήσεις: η μία περνάει, η άλλη παίρνει
`SLOT_TAKEN`. Επαληθευμένο ζωντανά.

**Αν μεταφέρεις τη βάση αλλού, αυτό είναι το πρώτο που πρέπει να
εξασφαλίσεις.** Χρειάζεται PostgreSQL με `btree_gist`. Η MySQL δεν το
έχει· εκεί θα χρειαστεί σειριοποίηση με κλειδώματα, που είναι χειρότερη
λύση.

### Οι συναρτήσεις

**Δημόσιες** (ο ρόλος `anon` μπορεί να τις καλέσει):

| Συνάρτηση | Τι κάνει |
|---|---|
| `availability(days)` | υπηρεσίες, ωράριο, κλεισίματα, πιασμένα διαστήματα |
| `book(...)` | κράτηση + email |
| `appointment_info(id, key)` | στοιχεία ραντεβού για τη σελίδα ακύρωσης |
| `cancel_appointment(id, key)` | ακύρωση από πελάτη |

**Διαχειριστικού** (ζητούν `p_pin` και το ελέγχουν στη βάση):

`admin_day`, `admin_add`, `admin_block`, `admin_close`, `admin_reopen`,
`admin_delete`, `admin_cancel`, `admin_set_pin`, `admin_export`

Η `admin_export` επιστρέφει **όλη** τη βάση με μία κλήση — τη χρησιμοποιεί
το `backup.mjs`. Εξαιρεί σκόπιμα τον κωδικό και το κλειδί του Resend.

Ο κωδικός ταξιδεύει με κάθε αίτημα. Γνωστός συμβιβασμός: αρκετός για ένα
κουρείο, όχι για σύστημα με πολλούς χρήστες. Αν χρειαστούν ποτέ
πολλαπλοί χρήστες, εδώ μπαίνει το Supabase Auth.

> **Ο έλεγχος του κωδικού δεν έχει όριο προσπαθειών.** Η `admin_ok()`
> είναι απλή σύγκριση. Όποιος έχει το δημόσιο κλειδί μπορεί να δοκιμάζει
> κωδικούς χωρίς φραγή — και με τη `admin_export` ένας σωστός κωδικός
> δίνει όλη τη βάση. Είναι το σοβαρότερο ανοιχτό θέμα· βλ. §10.

### Email

Φεύγουν **από τη βάση**, ασύγχρονα, με `pg_net`. Δεν καθυστερούν την
κράτηση: η βάση απαντάει στον πελάτη αμέσως και το email φεύγει από πίσω.

Η `send_email_()` είναι **σιωπηλή στα σφάλματα** — σκόπιμα. Αν πέσει ο
πάροχος, η κράτηση δεν πρέπει να χαλάσει. Το ραντεβού είναι πιο σημαντικό
από το email.

Ο πάροχος είναι **ρύθμιση, όχι κώδικας**:

```sql
update settings set value = 'https://api.άλλου.com/send' where key = 'email_endpoint';
update settings set value = 'το_κλειδί'                   where key = 'email_key';
```

Ποιος παίρνει τι:

| Γεγονός | Πελάτης | Κατάστημα |
|---|:---:|:---:|
| Νέα κράτηση | ✉ (αν έδωσε email) | ✉ |
| Ακύρωση από πελάτη | — | ✉ |
| Ακύρωση από κατάστημα | ✉ | — |

### Να μην κοιμηθεί η βάση

Το δωρεάν Supabase **παγώνει το project μετά από 7 μέρες χωρίς καμία
κλήση**, και τότε δεν ξυπνάει μόνο του: κάποιος πρέπει να πατήσει
*Restore* στον πίνακα ελέγχου. Μέχρι τότε το site είναι σπασμένο.

Δύο ανεξάρτητα χρονόμετρα το αποτρέπουν:

**1. cron-job.org (το κύριο).** Δύο εργασίες, ωριαίες, με ειδοποίηση
αποτυχίας στο email:

| | Βάση | Site |
|---|---|---|
| URL | `<SUPABASE_URL>/rest/v1/rpc/availability` | η διεύθυνση του site |
| Μέθοδος | **POST** | GET |
| Headers | `apikey`, `Authorization: Bearer <anon key>`, `Content-Type: application/json` | — |
| Body | `{"days":1}` | — |
| Επιτυχία | HTTP 200, απάντηση `{"ok" : true, ...` | HTTP 200 |

Με GET αντί POST παίρνεις 404· χωρίς το `Bearer` μπροστά από το κλειδί
παίρνεις 401.

**2. `.github/workflows/keepalive.yml` (δεύτερο δίχτυ).** Μία κλήση την
ημέρα. Εξαρτάται από commits — το GitHub σταματάει τα προγραμματισμένα
workflows μετά από 60 μέρες χωρίς αλλαγή στο repo. Γι' αυτό δεν είναι
το κύριο.

> Το `anon key` είναι δημόσιο εκ σχεδιασμού και σωστά βρίσκεται εκεί.
> Ο κωδικός του διαχειριστικού **δεν** μπαίνει ποτέ σε τέτοια υπηρεσία.

## 7. Ιδιαιτερότητες που θα σε μπερδέψουν

Αξίζει να τις ξέρεις πριν «διορθώσεις» κάτι που δεν είναι χαλασμένο.

**Ελληνικά κεφαλαία χωρίς τόνους.** Η `toUpperCase()` της JavaScript
κρατάει τον τόνο: `'Κλειστά'` → `'ΚΛΕΙΣΤΆ'`. Λάθος στα ελληνικά. Η
`H.grUpper()` το διορθώνει, και χειρίζεται και τους διφθόγγους
(Μάιος → ΜΑΪΟΣ). **Μη χρησιμοποιείς `text-transform: uppercase` σε
ελληνικά** — χρησιμοποίησε `H.fixGreekCaps()`.

**Γραμματοσειρές.** Πολλές δημοφιλείς του Google Fonts **δεν έχουν
ελληνικά** (Archivo, Space Grotesk, Anton, Oswald, Instrument Sans...).
Πριν βάλεις γραμματοσειρά, κατέβασε το CSS της και ψάξε το σχόλιο
`/* greek */`. Ο έλεγχος με regex τύπου `U+03` δίνει ψευδώς θετικά.

**Ώρα Αθήνας.** Ο server είναι UTC. Οι μετατροπές γίνονται με
`H.athens()` / `H.nowAthens()` (κόλπο με `Intl.DateTimeFormat`). Μη
χρησιμοποιείς σκέτο `new Date()` για ώρες ραντεβού.

**Ενσωματωμένα παράθυρα εφαρμογών.** Σε Messenger/Instagram/Viber το iOS
μπλοκάρει σιωπηλά τα κατεβάσματα — το κουμπί `.ics` δεν κάνει τίποτα. Η
`H.inApp()` το ανιχνεύει και εμφανίζεται προειδοποίηση «άνοιξέ το στο
Safari».

**Η `replace()` της JavaScript και το `$$`.** Σε συμβολοσειρά
αντικατάστασης, το `$$` σημαίνει «ένα κυριολεκτικό `$`». Έτσι χάλασε ένα
SQL patch (`end $$;` → `end $;`). Για επεξεργασία SQL από script,
χρησιμοποίησε `split().join()`.

**`admin_reopen` σβήνει ΟΛΟ το διάστημα** που περιέχει τη μέρα, όχι μόνο
τη μέρα. Το διαχειριστικό προειδοποιεί.

## 8. Όταν κάτι σπάσει

**Το site δεν ανοίγει** → GitHub → Actions → κοίτα το τελευταίο
`pages-build-deployment`. Αν το domain δεν λύνει, έλεγξε ότι υπάρχει
αρχείο `CNAME` στη ρίζα του repo.

**Ώρες δεν φορτώνουν, «δοκίμασε ξανά»** → η βάση δεν απαντάει.
Supabase dashboard: μήπως είναι **paused**; Πάτα *Restore*. Τα δεδομένα
δεν χάνονται.

**Ήρθε ειδοποίηση από το cron-job.org ή το keepalive** → το ίδιο, κάτι
δεν απαντάει. Είναι έγκαιρη προειδοποίηση, όχι σφάλμα του εργαλείου.
Κοίτα πρώτα αν το project στο Supabase γράφει *paused*.

**Δεν φεύγουν email** → με τη σειρά:

```sql
-- τρέξε ΧΩΡΙΣ RLS (ο SQL Editor το ρωτάει)
select key, length(value) from settings where key like 'email%';
select status_code, content, created from net._http_response order by id desc limit 5;
```

Κενό `email_key` → δεν έχει μπει το κλειδί. `403` με αναφορά σε
«testing» → δεν έχει επαληθευτεί domain στο Resend, οπότε στέλνει μόνο
στη διεύθυνση του λογαριασμού.

**Τα διαγνωστικά `select` γυρίζουν άδεια** → τα έτρεξες **με** RLS. Οι
πίνακες είναι κλειδωμένοι. Ξανατρέξ' τα χωρίς.

**Διπλή κράτηση εμφανίστηκε** → δεν πρέπει να μπορεί. Έλεγξε ότι υπάρχει
ακόμα ο περιορισμός:

```sql
select conname from pg_constraint where conname = 'appointments_no_overlap';
```

## 9. Παράδοση σε άλλον

### Μεταφορά λογαριασμών

1. **GitHub** — **και τα δύο** repos, `hairmania-source` και `hairmania`:
   Settings → Transfer ownership. Δωρεάν, με ανακατεύθυνση από την παλιά
   διεύθυνση.
2. **Supabase** — πρόσθεσε τον νέο ιδιοκτήτη ως Owner του οργανισμού.
3. **Resend** — φτιάξε τον λογαριασμό στο email του καταστήματος.
4. **cron-job.org** — δύο χρονόμετρα (βάση + site). Αν αλλάξει
   ιδιοκτήτης, πρέπει να ξαναφτιαχτούν στον νέο λογαριασμό, αλλιώς οι
   ειδοποιήσεις πάνε στο παλιό email. Δες §6 για τις τιμές τους.
5. **Domain** — στο όνομα του καταστήματος από την αρχή. **Μόλις μπει,
   άλλαξε και τη διεύθυνση στο χρονόμετρο του site.**
6. **Μυστικά** — κωδικός διαχειριστικού, κλειδί Resend, κωδικός βάσης.
   Ζουν σε διαχειριστή κωδικών (Bitwarden), ποτέ σε έγγραφα ή μηνύματα.
   Στην παράδοση μοιράζεται ο φάκελος· η πρόσβαση ανακαλείται με ένα κλικ.

### Αντίγραφα ασφαλείας — καθημερινή χρήση

**Το δωρεάν πλάνο του Supabase δεν κρατάει κανένα αντίγραφο.** Ένα λάθος
`delete`, ή διαγραφή του project, σημαίνει οριστική απώλεια.

```bash
node backup.mjs
```

Ο κωδικός διαβάζεται από αρχείο `backup-pin.txt` δίπλα στο script (το
`.gitignore` το κρατάει έξω από το repo). Εναλλακτικά `--pin ΟΚΩΔΙΚΟΣ`,
αλλά τότε ο κωδικός μένει στο ιστορικό της γραμμής εντολών.

Κατεβάζει τα πάντα σε `backups/backup-ΗΗΗΗ-ΜΜ-ΗΗ_ΩΩΛΛ.json`. Δεν τυπώνει
ονόματα ή τηλέφωνα στην οθόνη, μόνο πλήθη.

**Πού ΔΕΝ πρέπει να καταλήξει:** ο φάκελος `backups/` έχει ονόματα και
τηλέφωνα πελατών. Δεν ανεβαίνει σε κανένα repo — το `.gitignore` τον
εξαιρεί, και το `publish.mjs` δεν τον αντιγράφει. Δεν μπαίνει ούτε σε
σημειώσεις ή κοινόχρηστους φακέλους.

Δεν είναι αυτοματοποιημένο. Αν το θέλεις, βάλε το παραπάνω στον
**Προγραμματιστή εργασιών των Windows** (μία φορά την εβδομάδα αρκεί), ή
πλήρωσε το Supabase Pro που κρατάει ημερήσια αντίγραφα μόνο του.

Ο κωδικός του διαχειριστικού και το κλειδί του Resend **δεν** μπαίνουν
στο αρχείο, επίτηδες.

### Επαναφορά από αντίγραφο

> **Η διαδικασία αυτή δεν έχει δοκιμαστεί ακόμα σε πραγματική επαναφορά.**
> Είναι γραμμένη σωστά κατά τη γνώμη μας, αλλά μέχρι να τρέξει μία φορά σε
> πρόχειρο project, θεώρησέ την υπόθεση.

Στον SQL Editor, **ΧΩΡΙΣ RLS**, αφού πρώτα έχεις τρέξει σε καθαρή βάση
το `schema.sql` και τα τρία patches, με τη σειρά:

```sql
-- Επικόλλησε τον πίνακα "appointments" από το αρχείο JSON μέσα στα εισαγωγικά.
insert into appointments
select * from json_populate_recordset(null::appointments, '[ ... ]'::json);

-- Το ίδιο για τα υπόλοιπα:
insert into closures select * from json_populate_recordset(null::closures, '[ ... ]'::json);
insert into services select * from json_populate_recordset(null::services, '[ ... ]'::json)
  on conflict (id) do update set name_el = excluded.name_el, price = excluded.price;
insert into hours    select * from json_populate_recordset(null::hours, '[ ... ]'::json)
  on conflict (dow) do update set ranges = excluded.ranges;
insert into settings select * from json_populate_recordset(null::settings, '[ ... ]'::json)
  on conflict (key) do update set value = excluded.value;
```

Μετά ξαναβάλε με το χέρι τα δύο μυστικά που δεν σώζονται:

```sql
update settings set value = 'ΚΩΔΙΚΟΣ'  where key = 'admin_pin';
update settings set value = 're_ΚΛΕΙΔΙ' where key = 'email_key';
```

> Αν η επαναφορά διαμαρτυρηθεί για `appointments_no_overlap`, το
> αντίγραφο έχει δύο ενεργά ραντεβού που πατάνε το ένα στο άλλο. Δεν
> γίνεται να συνέβη κανονικά — σημαίνει ότι κάποιος πείραξε δεδομένα με
> το χέρι. Βρες τα με το ερώτημα της ενότητας 8 και διόρθωσε πρώτα.

### Πλήρες αντίγραφο με pg_dump

Για παράδοση ή μετακόμιση, όπου θες **και** τη δομή. Το connection string
είναι στο Supabase → Settings → Database.

```bash
pg_dump "postgresql://postgres:ΚΩΔΙΚΟΣ@db.<ref>.supabase.co:5432/postgres" \
  --no-owner --no-acl -f hairmania.sql
```

Ανεβαίνει σε **οποιαδήποτε** PostgreSQL. Καμία εξάρτηση από το Supabase
στα ίδια τα δεδομένα.

### Μετακόμιση σε άλλη υποδομή

- **Frontend** — αντιγράφεις τον φάκελο, τρέχει οπουδήποτε. Μηδέν κόπος.
- **Βάση** — `pg_dump` / `pg_restore` σε οποιαδήποτε PostgreSQL 14+ με
  `btree_gist`.
- **Στρώμα HTTP** — οι κλήσεις πάνε στο PostgREST, που είναι ανοιχτό
  λογισμικό και σηκώνεται μόνο του. Εναλλακτικά, γράφεις λεπτό API που
  καλεί τις ίδιες συναρτήσεις· η `db.js` είναι ένα αρχείο 128 γραμμών και
  είναι το μόνο σημείο που ξέρει τη διεύθυνση.

Ρεαλιστικά: μία με δύο μέρες, όχι ξαναγράψιμο.

## 10. Γνωστά κενά

Ειλικρινής λίστα, με σειρά σοβαρότητας. Τα τρία πρώτα θέλουν λύση πριν
από οποιαδήποτε παράδοση σε επιχείρηση.

| Κενό | Επίπτωση | Λύση |
|---|---|---|
| **Καμία φραγή προσπαθειών στον κωδικό** | με το δημόσιο κλειδί δοκιμάζει κανείς κωδικούς χωρίς όριο· ένας σωστός δίνει όλη τη βάση | πίνακας αποτυχημένων προσπαθειών και κλείδωμα — **η πρώτη προτεραιότητα** |
| **Η επαναφορά δεν έχει δοκιμαστεί** | σε πραγματική ανάγκη μπορεί να βγει κάτι που δεν προβλέφθηκε | μία δοκιμή σε πρόχειρο project Supabase |
| **Φιλοξενία στο GitHub Pages** | οι όροι του απαγορεύουν τη χρήση για επιχείρηση | μεταφορά πριν την παράδοση ή το δεύτερο κατάστημα — `ΚΟΣΤΟΛΟΓΙΟ.md` Β2 |
| Ωράριο και υπηρεσίες σε δύο μέρη | αλλαγή μόνο στο ένα = το site λέει άλλα από όσα δέχεται | χειροκίνητος συγχρονισμός, §5 |
| Τα αντίγραφα θέλουν χέρι | αν δεν τρέξει κανείς το `backup.mjs`, το τελευταίο αντίγραφο παλιώνει | Προγραμματιστής εργασιών Windows, ή Supabase Pro |
| Καμία εγγύηση διαθεσιμότητας | αν πέσει το Supabase, περιμένεις | ούτε το Pro δίνει εγγύηση· μόνο το Enterprise |
| Δωρεάν βαθμίδα «κοιμάται» στις 7 μέρες | το site σπάει **και η βάση δεν ξυπνάει μόνη της** — θέλει *Restore* από τον πίνακα | καλύπτεται από το cron-job.org (ωριαία), με το keepalive σαν δεύτερο δίχτυ |
| Ο κωδικός ταξιδεύει σε κάθε αίτημα | αποδεκτό για έναν χρήστη | Supabase Auth αν χρειαστούν πολλοί |
| Χωρίς επαληθευμένο domain, τα email πάνε μόνο στον ιδιοκτήτη | οι πελάτες δεν παίρνουν επιβεβαίωση | domain + DNS στο Resend |
| Οι φωτογραφίες αλλάζουν μόνο από προγραμματιστή | κάθε αλλαγή θέλει `publish` | αν το ζητήσει ο ιδιοκτήτης |
| Καμία αυτοματοποιημένη δοκιμή | οι έλεγχοι γίνονται με το χέρι | αν μεγαλώσει το έργο |
